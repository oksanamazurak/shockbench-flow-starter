# Параметри `agents/mpc`

Значення за замовчуванням задані в `PARAMS` у `agents/mpc_lp/agent.py`. `agents/mpc_lp/params.json`
їх перекриває (`PARAMS |= json.load(...)` при імпорті модуля). Чинне значення — з `params.json`,
якщо ключ там є.

Словник з ключами `"tiny"` / `"small"` / `"full"` означає, що значення вибирається за
`static["instance"]["kind"]`. Наразі так працюють лише `upstream_floor` і `fuel_mult`. Якщо замість
словника записати одне число, воно застосовується на всіх мережах.

"Train" нижче — тренувальний root `entropy=20261004` (8 episodes, якщо не вказано інше); "dev" — 20
публічних dev episodes.

## Обґрунтування

**`H = 16`.** Ланцюг wafer → fab (`tau` 6–8) → OSAT (2) → лейн до sink триває 14+ тижнів. На small
H × `terminal_scale` дає плато близько 0.61 (train), різниця ≤ 0.002; H = 16 трохи кращий на tiny.

**`terminal_scale = 0.25`.** Без terminal value LP не бачить сенсу відправляти wafer, бо чип з'явиться
після кінця горизонту. tiny (`all_but_grid`, H = 10): 0 → 0.39, 0.25 → 0.44 (train). На small від 0.1
до 0.5 різниця ≤ 0.004.

**`warn_b = −5` і ваги повідомлень.** Підібрані `07_mpc_policy_search` на tiny ще для Stage 1. При
`warn_b = −5` сигмоїда майже завжди дає `p_warn ≈ 1`, тож прогноз на h ≥ 1 вважає протоки майже
закритими. Для лейнів LP це працює як обережність. Але саме через це `reroute_forecast` провалюється:
прогноз називає закритими майже всі протоки попереду. Повторний тюнінг на small (8×10) значимого
покращення не дав.

**`tariff_bump = 0.085`.** Виміряно на 24 episodes tiny (entropy 20261004): усі tariff-повідомлення
адресовані регіону й товару. Тариф на імпорт зростав у ~45% випадків, у середньому на ~0.2, отже
очікуваний приріст ≈ 0.085. За каналами: formal 0.079, informal 0.088, final 0.082, тому ваги рівні.
Ефект: small +0.0003 (не значимо), регресу нема.

**`lp_scope = "all_but_grid"`.** Модель виробництва дає LP ціну для всіх шипментів чипів і wafer.
Паливо LP оцінити не може, бо споживання grid не змодельоване. Варіант `"demand"` (Stage 1) на small
поступається: 0.5500 проти 0.6107 (train, з `upstream_floor` small = 0).

**`upstream_floor`.** На tiny LP без нижньої межі недогодовує ланцюг перед кризою; у ep 4–5 нестача
коштувала +339 / +168 млн $. Train tiny: 0 → 0.50, 0.5 → 0.74, **0.8 → 0.78**, 1.0 → 0.776. На small
навпаки, найкраще без межі: train 0 → **0.6107**, 0.3 → 0.591, 0.45 → 0.572, 0.6 → 0.563, 0.7 → 0.558.
Для full перебору не було; взято значення small, перевірка на 6 dev episodes дала +0.059.

**`fuel_mult`.** На джерелах палива виконується ≈ стільки, скільки запитано, тож обмеження — сам
запит простого правила (`u0`). Train small: ×1 0.6107, ×1.5 0.6174, ×3 0.6205, ×10 0.6223, ×100 0.6225.
Dev small з ×10: 0.558 → **0.610** (+0.052, значимо). На tiny ×10 погіршує (−0.020, значимо), тому там
1. Full з ×10: +0.0085 (6 episodes, не значимо).

**`model_grids = False`.** Train small: увімкнено 0.536; з `terminal_scale` 0.5 — 0.601; з останнім
відрізком у grid, відданим простому правилу, — 0.531; вимкнено — 0.611. На tiny ≈ без змін.

**`reroute = False`.** Train small: за прогнозом 0.117; за фактичною відкритістю з порогами 0.5 / 0.2 /
0.1 / 0.02 — 0.49 / 0.58 / 0.60 / 0.6105; вимкнено — 0.6107.

## Як змінювати

- Новий параметр додавати в `PARAMS` з коментарем (що робить, значення, звідки цифра).
  Якщо його треба шукати, додати в `07_mpc_policy_search.py`: масиви `LOWER` / `UPPER`,
  `start_params`, `write_candidate`.
- Змінювати `params.json` лише за результатом `sbf compare` на dev.
- `07_mpc_policy_search.py` записує в `params.json` кандидата лише 16 чисел; ключів, яких він не
  пише (`lp_scope`, `upstream_floor`, `fuel_mult`, `terminal_scale`, ...), кандидат бере з `PARAMS`
  у коді, а не з `params.json`.
